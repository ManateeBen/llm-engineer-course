## why

11-0 讲清了"变在哪"，本单元讲"怎么迁"。

先破除一个幻觉：迁移的主要工作量**不是写代码**。真正吃掉工期的是另外两件事——**精度对齐**（怎么证明换平台后模型还是原来那个模型）和**性能归因**（慢了 30%，到底是哪几个算子、又是为什么）。代码重写往往只占三成，剩下七成在验证与调优。

还有一个更常见的失败模式：团队一上来就重写算子，写完发现 CANN 里有现成的高阶 API 能拼出来，白干两周。**所以第一步永远是盘点，不是动手。**

## body

### 1 迁移的四个层次：先定位自己站在哪

自下而上，迁移可能触及四层，成本量级差两个数量级：

| 层 | 你要动什么 | 典型工作量 |
|---|---|---|
| **L1 框架层** | `import torch_npu`、替换 device 字符串、通信后端换 HCCL | 小时~天 |
| **L2 算子库层** | 把 cuBLAS/cuDNN 调用换成 CANN 算子库（aclnn 接口） | 天 |
| **L3 自定义算子层** | CUDA kernel 用 Ascend C / TileLang 重写 + Tiling + 流水 | 人周/算子 |
| **L4 通信与并行层** | NCCL → HCCL、并行策略按新拓扑重调 | 天~周 |

**决策规则**：能用 L1/L2 解决的绝不进 L3。判据是——你的算子能否由 CANN 现成算子**组合**出来（哪怕多几次调用）。组合的冗余开销通常远小于自研算子的开发与维护成本。

### 2 Ascend C 的多层级 API：按"控制力/生产力"选档

Ascend C 的设计思想是给出一条**从易到难的光谱**，让你按需取用（CANN 社区版文档的分层）：

| 层级 | 抽象程度 | 适合什么 | 代价 |
|---|---|---|---|
| **算子模板库** | 最高 | 常见算子的完整实现参考，改改参数就能用 | 灵活性最低 |
| **高阶 API** | 高 | 单核常见算法已封装（如 Matmul、Softmax 的高级接口），开箱即用 | 细节不可控 |
| **基础 API** | 中 | 以单指令为抽象的 C++ 类库，基于 Tensor/Layout 编程 | 要自己排流水 |
| **语言扩展层（C API）** | 低 | 纯 C 接口，指针与数组内存分配，完整开放芯片能力 | 写起来最累 |
| **Python 前端（PyAsc / PyPTO）** | 高~低 | 用 Python 写高性能算子；PyPTO 支持 Tile 粒度与流水编排 | 生态较新 |

**选型判据**：先看算子模板库与高阶 API 能否覆盖；覆盖不了再下探。**每往下一层，生产力掉一档、控制力涨一档**——这是一个明确的取舍，不是"越底层越厉害"。

2026 年的一个重要变化：**昇腾 950 代际新增 SIMD/SIMT 混合编程与 RegBase 编程模式**。含义是：

- **SIMD**（单指令多数据）：适合**连续、规整**的数据并行，如连续数据累加
- **SIMT**（单指令多线程）：适合**离散、分支**的访问，如 gather/scatter 这类不规则访存
- **混合模式**：允许在一个 kernel 内自由切换。典型例子是 `gather and add`——先用 SIMT 做离散访存，再切 SIMD 做连续累加
- **RegBase**：把数据搬运与寄存器计算的控制权交给开发者，用于压榨极限性能

> 这条升级的意义是：过去只能"迁就硬件"（把不规则算子硬塞进 SIMD 模型），现在可以"按数据特征选执行模型"。**它把一类原本很难写的算子变成了可写的。**

### 3 PTO-ISA：用"Tile 级虚拟指令"换代际兼容

写底层算子最痛的一点是：**每代硬件都要重写**。PTO-ISA 的设计目标正是切断这个循环。

它的定位（据华为公开材料）：

- **面向 Tile 的指令集**：指令操作的对象是"一块数据"而非标量/单个向量
- **8 大类、120+ 条虚拟指令**：覆盖基本运算、数据搬运、通信等
- **代际兼容**：算子源码可跨代迁移——因为虚拟指令由下层编译器映射到具体硬件指令，硬件换了只需换映射
- **Auto / Manual 双模式**：Auto 让编译器自动优化，Manual 让开发者细粒度控制底层资源

**这与 TileLang 的关系**：TileLang 是更高一层的 tile 级 DSL（Python 风格），在昇腾侧经 Ascend C API 落到 PTO ISA。两者是"高级语言 → 虚拟指令集 → 物理指令"的上下游关系，不是竞争关系。

**对你意味着什么**：如果要写长期维护的自定义算子，**优先走 TileLang / PTO 这条"代际兼容"的路**，而不是直接写死在某一代的物理指令上。这等于给未来的硬件升级买保险。

**跨平台这一层还有个现成的例子**：DeepSeek 的 TileKernels 暴露**同一套 Python API**，自动选择 NVIDIA 或昇腾后端；DeepGEMM-Ascend 与 NVIDIA 版保持 API 兼容；DeepEP-Ascend 的公开 buffer 接口与 NVIDIA 版对齐。**这套设计的意图很明确——让上层模型代码不感知硬件差异。** 迁移时优先找这类"同源双后端"的库，能省掉大量适配代码。

### 4 迁移五步法

#### 第一步：算子盘点（Op Inventory）

不要凭感觉，用工具跑一遍，得到三张清单：

1. **全部算子及其调用次数、耗时占比**（用 profiling 工具抓，不要靠读代码猜）
2. **已有现成实现的**（CANN 算子库、高阶 API、模板库）
3. **缺失的**（需要自己写）

输出的决策依据是耗时占比：**占比 <1% 的算子，即便没有现成实现，也应该先用"能跑就行"的朴素实现顶上**。优化顺序严格按占比降序。

#### 第二步：替换与适配

按 §1 的层次从 L1 往上走。这一阶段的工程纪律：

- 每替换一批算子就跑一次回归，不要攒到最后
- 保持**双平台可运行**（通过开关切换），这样任何一步出错都能立刻对照 GPU 侧结果
- 通信层换成 HCCL 后，语义与 NCCL 基本一致，但要重新测带宽与延迟（承 11-0 §5 的 Ring AllReduce 模型）

#### 第三步：精度对齐（这一步最容易被跳过，也最容易出事）

**要证明的不是"loss 差不多"，而是"每一层输出的分布一致"**。具体做法（逐层对比）：

对第 \(\ell\) 层，取 GPU 侧输出 \(y^{(\ell)}_{\text{gpu}}\) 与昇腾侧输出 \(y^{(\ell)}_{\text{npu}}\)，至少看三个量：

\[
\text{相对误差：}\quad
\varepsilon_{\text{rel}} = \frac{\|y_{\text{npu}}-y_{\text{gpu}}\|_2}{\|y_{\text{gpu}}\|_2}
\qquad
\text{余弦相似度：}\quad
\cos\theta = \frac{\langle y_{\text{npu}},\,y_{\text{gpu}}\rangle}{\|y_{\text{npu}}\|\,\|y_{\text{gpu}}\|}
\]

以及（对 logits/分布类输出）承 1-1 的 **KL 散度** \(\mathrm{KL}(p_{\text{gpu}}\|p_{\text{npu}})\)。

**为什么必须逐层而不是只看最终结果？** 因为误差会累积。设每层引入相对误差 \(\varepsilon\)，\(L\) 层后按最坏情况串联：

\[
(1+\varepsilon)^{L} \;=\; \exp\!\bigl(L\ln(1+\varepsilon)\bigr)
\;\approx\; \exp(L\varepsilon)
\;\approx\; 1 + L\varepsilon \quad (\text{当 } L\varepsilon \ll 1)
\]

即**总误差约为 \(L\varepsilon\)**——每层看起来"只有万分之一误差"，\(L=80\) 层、加上每层若干子算子，总误差可以到百分量级。若某层误差偏大（比如量化或近似算子），它会主导整个链条。

**验收判据建议**（按任务定，不要一刀切）：
- 隐藏层：\(\varepsilon_{\text{rel}}\) 量级与 bf16 自身的跨 GPU 版本差异相当（即"换卡不比换卡版本更差"）
- logits：余弦相似度 > 0.999，KL 散度在可接受阈值内
- 生成任务：同一 prompt、贪心解码下，前 \(K\) 个 token 完全一致的比例
- 训练：前 \(N\) 步的 loss 曲线与 GPU 侧逐点偏差在噪声范围内（承 5-4 的噪声底概念）

**确定性等级的坑**：CANN 提供确定性等级设置（0 关闭 / 1 确定性 / 2 强一致性），PyPTO 的 JIT 入口会自动读取 torch_npu 的进程级设置写入编译配置，以保证编码侧与框架侧一致。**做精度对齐前务必先固定确定性等级**，否则你测到的差异里混着"浮点归约顺序不同"的噪声（承 8-8 §4），会误导归因。

#### 第四步：性能剖析与归因

慢了怎么办？回到 8-1 的 roofline：

\[
\text{先看占比} \to \text{再看该算子的算术强度} \to \text{判区} \to \text{选手段}
\]

昇腾侧特别要注意的三件事：

1. **Cube 利用率**：矩阵算子有没有真正走 Cube 单元（数据格式或形状不对会掉到 Vector 上跑，慢一个量级）
2. **流水编排**：搬运与计算有没有重叠。显式分层存储的好处是上限高，坏处是没排好就直接退化成串行
3. **同步开销**：核内同步、核间流水是否过度（CANN 9.2.0 已支持自动核内同步与自动核间流水编排，优先用自动）

工具侧：MindStudio / Profiling 采集数据，配合 CANNBot 这类算子生成 Agent（据华为公开材料，常见 Vector 类算子可缩短到小时级）做初版实现，再人工调优。

#### 第五步：回归与长期维护

- 建立**双平台回归基线**（同一批 prompt、同一套指标、自动化跑）
- 记录每个自研算子的**验收条件与实测数字**，硬件/驱动/CANN 升级后重跑
- 明确**代际维护责任人**——这是自研算子最容易被遗忘的长期成本（8-1 §7）

### 5 一个现实的性能参照系

迁移前该有怎样的性能预期？看昇腾 950 上的公开实测（厂商自测、CANN 9.20，非独立复现）：

| 组件 | 场景 | 实测 | 相对硬件极限 |
|---|---|---|---|
| DeepGEMM-Ascend | BF16 稠密 GEMM | — | **99.8%** |
| DeepGEMM-Ascend | FP8 GEMM | — | 约 99.5% |
| FlashMLA | 稀疏注意力 prefill | 410 TFLOPS | 约 95% |
| FlashMLA | 稀疏注意力 decode | 360 TFLOPS | 约 83% |
| DeepEP-Ascend | dispatch 带宽（EP ≤ 32） | — | 90~95% |

**怎么读这张表**：规整 GEMM 已贴近极限（说明迁移后矩阵乘的性能不该成为瓶颈）；**稀疏注意力与通信还有 5~20% 的空间**，且这些数字依赖形状、并行规模、拓扑与模型版本。

**三条必须同时记住的告诫**（这些是仓库文档自己给出的）：
1. 数字来自维护方公开测试，**未经独立验证**，且依赖矩阵形状、专家并行规模、网络拓扑、数据格式与模型版本
2. **算子微基准不能直接换算成端到端请求延迟**
3. 各仓库的依赖（CANN、torch_npu、Python、编译器）**未作为统一安装矩阵验证过**——也就是说，把它们拼在一起能跑通这件事，本身就要花时间

### 6 什么时候不该迁

反面同样重要。以下情况应暂缓或放弃：

- **模型结构还在快速迭代**：今天适配的形状下周就变了，适配代码反复作废
- **只用到长尾算子且无现成实现**：除非该算子占比极高，否则性价比差
- **团队没有 profiling 能力**：无法归因就无法优化，迁过去只会得到一个"慢且不知道为什么慢"的系统
- **没有双平台对照环境**：精度对齐无从谈起（无法区分"平台差异"与"实现 bug"）

> 一条经验：**先迁一个完整的、尽量小的模型端到端跑通，再谈优化。**端到端跑通暴露的是"缺什么"，而缺什么才是真实工作量的主要部分——这个信息比任何微基准都值钱。

## ex

**练习 1（对应退出标准 1）**
你的项目用了 3 个自定义 CUDA 算子（一个 fused bias+gelu、一个自定义稀疏注意力、一个 MoE 路由 top-k）。按 §1 的四层模型，分别判断它们各落在哪层、优先级如何排，并说明哪个最可能根本不用自己写。

**参考答案：**
① fused bias+gelu：**L2**——逐元素融合是 CANN 算子库与高阶 API 的常规覆盖对象，极可能现成就有（或用两个现成算子 + 融合开关解决）。**优先级：先查库，最可能不用写。**
② 自定义稀疏注意力：**L3**——形态新颖，多半没有现成实现，需要 Ascend C/TileLang 重写。但它是性能关键路径，值得写。
③ MoE 路由 top-k：**L3，但可能被现成方案覆盖**——CANN 9.2.0 已针对 Ascend 950 优化 TopK 的 RadixSelect 路径；且 DeepSelect 这类库专门做 TopK 热路径。**先查再写。**
优先级排序：先做①的"查库替换"（成本最低），再评估③是否有现成实现，最后投入②。**顺序依据是"成本/收益比"而非技术难度。**

**练习 2（对应退出标准 2）**
解释 SIMD 与 SIMT 的差别，并说明为什么昇腾 950 的"混合编程"对 `gather and add` 这类算子特别有价值。再举一个你认为更适合纯 SIMD 的算子，说明理由。

**参考答案：**
SIMD：一条指令同时处理**连续、规整**的多个数据，所有 lane 走同一条执行路径；SIMT：多线程各自执行、允许**分支与离散访存**（每个线程可有独立的地址与路径）。
`gather and add`：先按索引从离散位置取数（地址不连续、需要 SIMT 的独立寻址能力），再对取回的数据做连续累加（规整、适合 SIMD 的宽向量）。**单一模式下必有一半是低效的**——纯 SIMD 处理不了离散 gather，纯 SIMT 浪费了连续累加的带宽。混合模式让两段各用最合适的执行模型。
纯 SIMD 更适合：**LayerNorm 的仿射变换**（\(y=\gamma\cdot\hat{x}+\beta\)）、逐元素激活、连续向量加——它们的访存连续、无分支、lane 行为一致，SIMD 的宽向量吞吐能吃满。

**练习 3（对应退出标准 3）**
为什么 PTO-ISA 的"Tile 级抽象"能实现代际兼容？请从"虚拟指令 → 物理指令"的映射关系说明，并指出这种设计把成本转移到了哪里。

**参考答案：**
算子源码只描述"对一块 Tile 做什么"（如搬运、乘加、归约），不描述具体用哪条物理指令、几个周期、什么寄存器布局。**硬件代际变化时，只需更新编译器里的"虚拟指令 → 物理指令"映射**，算子源码不动——这就是代际兼容的来源。
**成本转移到**：① **编译器**（必须持续为新硬件提供高质量映射，映射质量决定性能）；② **性能可预测性下降**（同一份源码在新硬件上的性能取决于映射质量，可能需要 Manual 模式介入调优）；③ **抽象泄漏风险**（遇到 PTO 表达不了的操作时，仍需下沉到底层，此时代际兼容失效）。
**判断**：这是典型的"用编译器复杂度换源码寿命"的取舍——对需要长期维护的自研算子划算，对一次性算子不划算。

**练习 4（对应退出标准 4）**
设某模型 80 层，每层引入的相对误差为 \(\varepsilon=1\times10^{-4}\)。用 \((1+\varepsilon)^L\) 估算最终输出的相对误差（一阶近似），并说明：若其中某一层的误差是 \(\varepsilon_1=1\times10^{-2}\)（比如一个量化近似的算子），它对总误差的贡献是其余层总和的多少倍？这给出什么工程指导？

**参考答案：**
均匀情况：\((1+10^{-4})^{80}\approx\exp(80\times10^{-4})=\exp(0.008)\approx1.008\)，即总相对误差约 **0.8%**。
若某一层是 \(10^{-2}\)：该层单独贡献约 1%，其余 79 层贡献约 0.79%，**该层贡献是其余总和的约 1.27 倍**——即**一个坏算子抵得上 100 个好算子**（\(10^{-2}/10^{-4}=100\) 倍）。
**工程指导**：精度对齐要**按层定位最大误差源**，而不是平均用力。找到那个 \(\varepsilon_1\) 最大的算子，把它的误差降一个量级，胜过把其余所有算子的误差再压一半。这也是"逐层对比"而非"只看最终结果"的实际价值——只有逐层才能定位到它。

**练习 5（对应退出标准 5）**
迁移后训练吞吐只有 GPU 侧的 70%。请按 §4 第四步给出你的归因流程（至少四步），并说明每一步分别要拿到什么数据、排除什么假设。

**参考答案：**
① **Profiling 拿耗时占比**：拿到算子级耗时 Top-10 与各自的占比，确认瓶颈是算子、通信还是调度空隙（排除"整体都慢"这种无法行动的结论）。
② **对 Top 算子算算术强度并判区**（承 8-1）：拿到每个算子的实际达成算力/带宽，与硬件峰值比。若某算子达成率 <50%，标记为候选（排除"已经跑满、只是硬件峰值低"的情况）。
③ **检查 Cube 利用率**：确认矩阵算子是否真正走了 Cube 单元（数据格式如 HiFloat8 vs FP8、形状对齐、layout 都会影响）。**这一步专门排除"掉了 Vector 路径"这个昇腾侧高频坑**——症状是矩阵算子慢一个量级。
④ **检查流水与同步**：看搬运与计算是否重叠、核内/核间同步是否过度。优先用 CANN 的自动核内同步与自动核间流水编排做对照实验（排除"人工排流水排错了"）。
⑤ **通信侧单独测**：用 HCCL 单独测 AllReduce/dispatch 带宽（对照 11-0 §5 的模型），确认不是通信拖累（尤其在 MoE 的 EP 场景）。

**练习 6（对应退出标准 6）**
团队计划把手写的 12 个 CUDA 融合算子迁到昇腾，预计"每个算子 2 人周"。作为技术负责人，你会如何重新评估这个计划？给出至少三条具体的纠正建议。

**参考答案：**
三条纠正：
① **先盘点再估工**（§4 第一步）：12 个算子中有多少已被 CANN 算子库/高阶 API/模板库覆盖？经验上融合类算子有相当比例是现成的，或可用 2 个现成算子 + 融合开关替代。**先跑 profiling 与库的比对，把"待写清单"从 12 个砍到真实数量**，再估工。
② **按耗时占比排序，而非平均用力**：若 12 个算子里 3 个占了 90% 的时间，那另外 9 个应该用朴素实现顶上（能跑就行），把人力集中到那 3 个。**"每个算子 2 人周"的平均主义是最贵的排法。**
③ **工期里必须包含精度对齐与回归**（§4 第三、五步）：2 人周通常只算了"写代码"，而真实工期里验证占大头。建议按 **代码 : 验证 ≈ 3 : 7** 重新估，并先建双平台对照环境（否则无法区分平台差异与实现 bug）。
补充：优先用 TileLang / PTO 这条代际兼容路径写，为后续硬件升级留余地；并明确代际维护责任人——这是最容易被漏掉的长期成本。
