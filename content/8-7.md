## why

8-1 讲完算子，你可能会以为"把算子写快，服务就快了"。真实情况是：**单算子跑到硬件峰值 99%，端到端延迟可能只降 4%**（8-1 练习 6 已经算过这笔账）。因为推理服务的瓶颈不在单次计算，而在三件"调度层"的事：

1. **显存怎么分** —— KV cache 要占几十 GB，分得碎不碎决定能同时跑多少请求
2. **请求怎么排** —— 一个 128K 的长 prefill 能把整批 decode 卡住几十毫秒
3. **阶段怎么拆** —— prefill 是算力受限、decode 是带宽受限，塞在同一张卡上必然互相干扰

这三条都不改模型、不改算子，纯靠系统设计。本单元讲推理引擎的核心机制，并以 2026 年 10 月开源的 **DeepInfer**（DeepSeek 支撑 V4.1-Flash 的生产引擎）为解剖对象——它是目前唯一公开的"真在生产上跑着的大规模 MoE + MLA 服务栈"。

## body

### 1 两个阶段：一个算力受限，一个带宽受限

自回归生成分两段，性质截然不同：

| | **prefill**（处理输入） | **decode**（逐个生成） |
|---|---|---|
| 输入形状 | \(N\) 个 token 一次进 | 1 个 token 一次进 |
| 主要算子 | 大 GEMM（\(M=N\)） | 瘦 GEMM（\(M=1\)）+ KV 读取 |
| 算术强度（承 8-1 §1） | \(I\approx\tfrac12 N\)，\(N\) 大时**算力受限** | \(I\approx\tfrac12\)，**带宽受限** |
| 显存流量 | 权重读一遍 + 激活 | **每个 token 都要把权重和 KV 全读一遍** |
| 关键指标 | **TTFT**（首 token 延迟） | **TPOT**（每输出 token 时间） |

用 8-1 的 roofline 判据立刻能读出两条硬结论：

- **prefill 要的是算力**：把它切成小块慢慢算不会减少总工作量，只是摊平了延迟（chunked prefill 的意义在于此，见 §4）
- **decode 要的是带宽**：单请求的 decode 无法靠"更好的 GEMM"加速，只能靠**把 batch 攒大**（让 \(M\) 变大，抬算术强度）或**减少要搬的字节**（KV cache 压缩 / 量化）

> 比喻：prefill 像一次性把一车货装上车（搬得多，力气大就行）；decode 像每次只送一个小包裹却要跑完整条路（路程/带宽才是成本）。所以 decode 的正确做法是"拼车"——一次送一百个包裹。

### 2 KV cache 的账：先算清楚它有多大

每个 token 在每层要缓存 Key 与 Value。对标准 MHA：

\[
\text{Bytes/token} \;=\; 2 \times L \times n_{\text{kv}} \times d_{\text{head}} \times b
\]

其中 \(L\) 层数、\(n_{\text{kv}}\) KV 头数、\(d_{\text{head}}\) 每头维度、\(b\) 每元素字节数（FP16 为 2）。以 7B/32 层/GQA 8 头/128 维/FP16 为例：\(2\times32\times8\times128\times2=131072\) 字节 \(\approx\) **128 KB/token**。一个 32K 上下文的会话就是 4 GB；并发 32 个这样的会话，**1 TB 显存都不够**。

这就是为什么 KV cache 管理是推理引擎的第一性问题。三条压缩路径：

1. **架构侧**：GQA/MQA 减头数（3-2）、MLA 低秩压缩（3-2）、跨层 KV 复用与稀疏索引
2. **数值侧**：FP8 KV、FP4 KV（E2M1 + 每 16 通道一个 E4M3 scale）
3. **系统侧**：把冷 KV 换到主机内存/SSD，需要时再取回

把它们叠起来能有多狠？看 2026 年的实测口径：DeepSeek-V4.1-Flash 通过 **CSA2 跨层复用 + FP4 KV**，把常驻 HBM 的全局 KV 压到 **890 字节/token**（约为上一版 V4-Flash 的 1/4）；再用 **SWA 有界重放**（只重放最近 \(n_{\text{win}}\) 个 token 来重建滑动窗口 KV，不必持久化 SWA KV），把需要落盘的持久 KV 压到约 1/8。1M token 上下文也能放进一台机器。

> 这条线的终点是：**KV cache 从"容量约束"退回为"带宽约束"**——不再是"放不放得下"，而是"取回来快不快"。判据变了，优化方向就跟着变。

### 3 显存管理：分页 vs 前缀树

#### PagedAttention：把 KV cache 当虚拟内存

朴素做法是为每个请求**预分配**一段连续显存（按最大长度），结果是灾难性的浪费：请求实际长度远小于上限，且长度不可预知。vLLM 的做法是把 KV cache 切成**固定大小的块**（如 16 个 token 一块），按需分配，用**块表**（block table）把逻辑顺序映射到物理块——和操作系统分页是同一个思想。

收益可以量化。设块大小 \(B\)，请求长度随机：

- 预分配方案浪费率 \(=1-\dfrac{\mathbb{E}[\text{实际长度}]}{\text{预留长度}}\)，典型 60~80%
- 分页方案的浪费只来自**最后一个块的内部碎片**，期望浪费 \(\tfrac{B}{2}\) 个 token，相对浪费率 \(\dfrac{B}{2\mathbb{E}[\text{长度}]}\)

取 \(B=16\)、平均请求 2000 token：分页浪费率 \(=16/(2\times2000)=0.4\%\)。**几乎零碎片**，这是 2~4 倍并发提升的来源。

#### RadixAttention：让"重复的前缀"只算一次

分页解决了"碎片"，但没解决"重复计算"。现实负载里前缀高度重复：多轮对话的历史、Agent 的系统提示、few-shot 示例、RL rollout 的同一道题采样多次。SGLang 的 RadixAttention 把已计算过的 KV 存进一棵**基数树**（radix tree，按 token 序列索引），新请求来了就沿树匹配最长前缀，只算剩余部分。

两者的差别在数学上是**命中粒度**：

- 分页 + 块级前缀缓存：命中要求前缀**对齐到块边界**，未对齐的尾部要重算。设块大小 \(B\)、共享前缀长 \(P\)，则重算量 \(\approx P \bmod B\)，期望 \(\tfrac{B}{2}\)
- 基数树：**token 级精确匹配**，重算量为 0

每轮省下的 prefill 工作量：

\[
\Delta\text{FLOPs} \;=\; \underbrace{\tfrac{B}{2}}_{\text{分页，每轮}}\quad\text{vs}\quad \underbrace{0}_{\text{基数树}}
\]

且这个差在**每轮对话都发生**——12 轮对话就是 \(12\times\tfrac{B}{2}\) 个 token 的纯浪费。这解释了为什么在 Agent/多轮场景，前缀命中率是比原始吞吐更重要的 KPI。

> 一句话：**分页管的是"空间浪费"，前缀树管的是"时间浪费"**。vLLM 也有自动前缀缓存（块级），SGLang 的基数树在任意深度、分支对话上更彻底。2026 年两者差距已在收敛。

### 4 调度：连续批处理与分块 prefill

#### 连续批处理（continuous batching）

朴素批处理等整批请求都生成完再放新请求进来，导致"短请求陪长请求耗到天亮"，GPU 利用率被拖垮。连续批处理的规则极简：**每个请求生成完一个 token 就让位，调度器立刻补一个新请求进来**。于是批的大小动态变化，卡上永远有活干。

#### 分块 prefill（chunked prefill）

连续批处理引入新问题：一个 128K 的 prefill 是一大块算力任务，插进来会把同批所有 decode 卡住——decode 的 TPOT 突然飙高（**generation stall**）。解法是把长 prefill 切成固定大小的块（如 512 token），每步只算一块，与 decode 混合调度。

**这里有个常见误解要澄清**：分块 prefill **不减少总工作量**，只是把 prefill 的计算摊到多个时间步，让 decode 的延迟抖动变小。总 FLOPs 不变，甚至因调度开销略增。它买的是**尾延迟（p99）**，不是吞吐。

#### 排队视角：为什么延迟会在高负载下爆炸

设请求到达率为 \(\lambda\)、服务率为 \(\mu\)，系统利用率 \(\rho=\lambda/\mu\)。对最常见的 M/M/1 排队模型，平均等待时间

\[
\mathbb{E}[W] \;=\; \frac{1}{\mu}\cdot\frac{\rho}{1-\rho}
\]

关键的不是分子，是 \(\tfrac{1}{1-\rho}\) 这一项：**\(\rho\to1\) 时延迟发散**。\(\rho=0.5\) 时等待是服务时间的 1 倍；\(\rho=0.9\) 时是 9 倍；\(\rho=0.95\) 时是 19 倍。

发散得有多快，可以对 \(\rho\) 求导看出——**边际恶化速度本身也是发散的**：

\[
\frac{d\,\mathbb{E}[W]}{d\rho}
\;=\; \frac{1}{\mu}\cdot\frac{(1-\rho)+\rho}{(1-\rho)^2}
\;=\; \frac{1}{\mu\,(1-\rho)^2}
\]

\(\rho\) 从 0.5 提到 0.6，等待时间增加约 \(0.56/\mu\)；从 0.9 提到 0.95，增加约 \(100/\mu\)——**同样的 5 个百分点，代价差了近 180 倍**。这不是"变慢一点"，而是二阶发散。

工程含义：**在线服务不能按峰值容量规划**。想让 p99 好看，\(\rho\) 通常要压在 0.7 以下——也就是说，你有 30% 的算力是"故意空着"的，买的是延迟确定性。这也解释了为什么厂商报告的"峰值吞吐"和你线上跑出来的差那么远。

### 5 阶段分离：把 prefill 和 decode 放到不同机器上

两阶段的性质不同（算力受限 vs 带宽受限、显存特征不同、批处理策略不同），塞在同一张卡上会互相干扰，且无法独立扩缩容。**PD 分离**（prefill/decode disaggregation）把两者拆成独立资源池：prefill 池算完把 KV 传给 decode 池。

收益用 Amdahl 式的份额分析：设 prefill 占总时间 \(p\)，decode 占 \(1-p\)。分离后各自可按最优配置独立扩展，理论加速上界为

\[
S_{\max} \;=\; \frac{1}{\max\bigl(p\cdot r_p,\;(1-p)\cdot r_d\bigr) + \text{传输开销}}
\]

其中 \(r_p,r_d\) 是分离后各阶段的相对耗时改善。实际收益取决于两件事：

- **负载形态**：输入重的 Agent 场景（prefill 占比高）收益最大，纯聊天场景收益小
- **传输代价**：KV 要从 prefill 池搬到 decode 池，\(N\) token \(\times\) 每 token 字节数 \(\times\) 并发数。用 §2 的数字，128K 上下文、890 字节/token 就是 114 MB/请求——**互联带宽不够时，传输会把收益全吃掉**

所以 PD 分离不是"永远更优"，而是一道**算力/带宽的权衡题**：只有当"分离带来的利用率提升"大于"KV 传输带宽成本"时才划算。这也是为什么它通常只在**高速互联域内**（同一个 scale-up 域）做。

### 6 MoE 服务的额外一层：专家并行与负载均衡

稠密模型只管 KV，MoE 模型还要管**专家路由**。以 384 个路由专家、每 token 激活 6 个为例：

- **专家并行（EP）**：专家分布在不同卡上，token 要经 dispatch 送到目标专家、算完再 combine 回来。这是 all-to-all 通信，量随并发 token 数 × top-\(k\) 增长
- **负载不均**：路由天然倾斜，某些专家收到的 token 是平均值的数倍。由于一个批次必须等**最慢的专家**，实际耗时由 \(\max\) 决定而非 \(\mathbb{E}\)：

\[
T_{\text{layer}} \;=\; \max_{e} T_e \;\geq\; \mathbb{E}_e[T_e]
\]

定义**不均衡因子** \(\kappa=\max_e T_e/\mathbb{E}_e[T_e]\)，则 MoE 层的效率上界是 \(1/\kappa\)。\(\kappa=2\) 意味着一半算力在空转。

**EPLB**（expert parallel load balancing）的解法：冗余部署热门专家（把高负载专家复制多份，按负载把 token 分给副本），配合路由偏置，把 \(\kappa\) 压回接近 1。代价是显存被复制的专家占掉一部分。

> 这一层是 MoE 服务与稠密服务最本质的差别：**稠密服务的调度对象是"请求"，MoE 服务的调度对象还要加一个"专家"**。8-1 表格里 DeepEP 解决的就是这层通信。

### 7 解剖 DeepInfer：一个真实的生产栈

2026 年 10 月，DeepSeek 开源了 **DeepInfer**（Apache 2.0）——支撑 DeepSeek-V4.1-Flash 线上服务的推理引擎。这是罕见的"把生产栈公开"的案例，值得逐层拆开看。

**它是什么**：基于 vLLM 构建，吸收了 SGLang 与 TensorRT-LLM 的思路，在其上叠加 DeepSeek 自研内核与并行策略。默认加载 V4.1-Flash-1017 权重。

**内核层**（承 8-1 §6）：FlashMLA（含稀疏注意力）、DeepGEMM、DeepEP、TileKernels、DeepSelect，以及自写 TileLang 算子。

**并行层**：Attention DP（注意力数据并行）、带均衡的上下文并行 CP、MoE 专家并行 EP + EPLB 负载均衡。

**调度层**：
- **DSpark 投机解码**：半自回归草稿生成（3 个 transformer block、128 token 窗口，一次草稿 5 个位置），小马可夫头建模草稿 token 间的依赖，置信度头预测接受率——调度器按**当前负载**为每个请求挑验证长度（这是它与传统投机解码的关键差别：验证长度是动态的）
- **SWA 有界重放**：滑动窗口模型只重放覆盖活动窗口所需的最近若干 token，砍掉长上文的冗余 prefill
- **异步调度**：CPU 侧的批次编排与加速器执行重叠
- **确定性推理**：batch-invariant inference（结果与批次组合无关）+ 确定性采样（同输入、同采样参数、同种子 → 同输出）

**能力边界（很重要）**：它**不含** KV cache 的持久化管理、prefill/decode 分离的执行编排、副本负载均衡、HTTP/鉴权/配额/可观测。换句话说——**它给你执行原语，服务层要你自己搭**。

**官方口径的性能**（4 张卡跑 prefill、64 张卡跑 decode，同一 scale-up 域内）：128K 上下文下 prefill 约 29K tokens/s/卡；decode 在"每用户 80 tokens/s"的交互速度下约 2200 tokens/s/卡；集群规模上约 155 万亿 tokens/天，TTFT 约 400ms、生成约 230 tokens/s（代码场景到 300）。

**怎么读这组数字**（三条纪律，与 8-1 §6 一致）：
1. 这是厂商自测、未经独立复现，且是**特定硬件配置与特定负载**下的数字
2. "155 万亿 tokens/天"是集群总量，除以卡数与时间才可比
3. 缺少 KV cache 管理与 PD 分离意味着：**你不能直接拿它当服务用**，它是一台引擎，不是一辆车

**配套还有一个值得单独提的东西**：`deepseek-recipe`（MIT）。很多团队本地部署开源权重后发现"比官方 API 笨"，病根常在**请求前后的格式转换**——提示词拼装、tokenize、输出解析。这个库把 OpenAI/Anthropic 等格式的请求转成统一的会话表示，严格按官方逻辑渲染提示词，再原样解析回去。**教训是：开源权重 ≠ 开源服务，协议层的对齐也是对齐。**

### 8 该盯哪些指标

| 指标 | 定义 | 为什么重要 |
|---|---|---|
| **TTFT** | 首 token 时间 | 决定"用户等多久才看到第一个字"，主要受 prefill 与排队影响 |
| **TPOT** | 每输出 token 时间 | 决定"读起来流不流畅"，受 decode 带宽与 batch 影响 |
| **吞吐** | tokens/s（集群级） | 决定成本；但要在**给定延迟约束下**比才有意义 |
| **前缀命中率** | 复用 token 数 / 总 prefill token 数 | Agent 场景下，提升它的收益常常大于提升原始吞吐 |
| **KV cache 利用率** | 已用 / 总量 | 接近 100% 时会开始抢占（重算或换出），是容量告警 |
| **p99 / p50 比** | 尾延迟倍率 | 接近 1 说明调度稳定；飙升说明有 stall（长 prefill 抢占） |

> 一条经验法则：**先定 SLO（如 p99 TTFT < 1s、TPOT < 50ms），再在这个约束下最大化吞吐**。脱离延迟约束比吞吐没有意义——把 batch 堆到无穷大，吞吐会很好看，但没人愿意用。

## ex

**练习 1（对应退出标准 1）**
一个 32 层、GQA 8 个 KV 头、每头 128 维、FP16 的模型，求每 token 的 KV 字节数。若服务 8000 token 的平均上下文、目标并发 64，需要多少 KV 显存？若改用 FP8 存 KV、并把 KV 头压到 1（MQA），又是多少？

**参考答案：**
原式 \(2\times32\times8\times128\times2=131072\) 字节 \(=128\) KB/token。8000 token \(\times\) 64 并发 \(=5.12\times10^5\) token，\(5.12\times10^5\times128\text{KB}=65.5\) GB。
FP8 且 MQA：\(2\times32\times1\times128\times1=8192\) 字节 \(=8\) KB/token，总计 \(5.12\times10^5\times8\text{KB}=4.1\) GB。**压缩 16 倍**（8 倍来自 KV 头数、2 倍来自位宽）。注意代价：MQA 会损失质量，FP8 KV 有精度损失，需按任务验收——这正是 8-8 要量化的事。

**练习 2（对应退出标准 2）**
分块大小 \(B=16\)，请求长度在 \([1, 4000]\) 均匀分布的近似下，对比"按最大长度 4000 预分配"与"分页（块 16）"两种方案的显存浪费率。再问：若块增大到 64，浪费率如何变、为什么实践中不无限增大块。

**参考答案：**
预分配：预留 4000、期望长度 2000，浪费率 \(1-2000/4000=50\%\)。
分页：只有最后一块内部碎片，期望 \(B/2=8\) token，浪费率 \(8/2000=0.4\%\)。
块增到 64：浪费率 \(32/2000=1.6\%\)。所以**块越大浪费越多**。但块太小也不行：块表元数据随块数线性增长（每块的块表项要被内核读取），且块小会降低块级前缀缓存的命中率（未对齐尾部占比上升）。实践中 16~32 是元数据开销、碎片、缓存命中率三者的折中。

**练习 3（对应退出标准 3）**
一段 3000 token 的系统提示被 20 轮对话共享。对比"块级前缀缓存（\(B=16\)）"与"token 级基数树"两种方案在 20 轮中多算的 prefill token 总数，并说明为什么这个差距在多轮/分支对话里会被放大。

**参考答案：**
块级：3000 与 16 对齐（\(3000=187\times16+8\)），未对齐尾部 8 token，每轮重算 8 个，20 轮共 160 token——看着不多。但若系统提示是 3007 token（尾部 15），每轮重算 15 个。更关键的是**多轮场景的命中深度**：第 \(k\) 轮的可复用前缀是 \(3000+\)前 \(k-1\) 轮的对话内容，基数树能在**任意深度**匹配（包括分叉的对话分支），块级缓存只能命中块边界对齐的部分，且分支对话各自缓存、难以共享。
**放大机制**：分支对话（如 beam/树搜索、RL rollout 采样同一道题多次）的可复用结构是树形，基数树天然表达树，块级缓存只能表达线性前缀——共享度越高，差距越大。SGLang 论文报告的 6.4 倍吞吐提升就来自这类负载。

**练习 4（对应退出标准 4）**
用 M/M/1 排队公式 \(\mathbb{E}[W]=\frac{1}{\mu}\cdot\frac{\rho}{1-\rho}\)，计算 \(\rho=0.5, 0.8, 0.9, 0.95\) 时的等待时间（以服务时间 \(1/\mu\) 为单位）。若你的 SLO 要求"等待不超过 3 倍服务时间"，\(\rho\) 最高能到多少？这对容量规划意味着什么？

**参考答案：**
\(\rho/(1-\rho)\)：0.5→1.0；0.8→4.0；0.9→9.0；0.95→19.0。
要求 \(\rho/(1-\rho)\le3\)：\(\rho\le3(1-\rho)\Rightarrow4\rho\le3\Rightarrow\rho\le0.75\)。
**含义**：为了满足延迟 SLO，你必须把利用率压在 75% 以下——**25% 的算力是买延迟确定性的保险费**。这也解释了为什么"按平均负载规划容量"必然翻车：平均负载下 \(\rho\) 看起来不高，但流量有突发，突发时 \(\rho\to1\)，延迟发散。

**练习 5（对应退出标准 5）**
什么情况下 PD 分离不划算？用"传输成本 vs 利用率收益"的框架分析：设每请求 KV 大小 \(K\) 字节、两池间传输带宽 \(W\)、并发请求率 \(R\)，写出传输占用的带宽表达式，并给出"划算"的判据。

**参考答案：**
传输带宽占用 \(=R\cdot K\)（每秒 \(R\) 个请求，每个搬 \(K\) 字节）。判据：

\[
R\cdot K \;<\; \eta \cdot W
\]

其中 \(\eta\) 是你愿意为 KV 传输让出的带宽比例（如 0.2）。超过这个值，传输就会与正常计算抢带宽，得不偿失。
代入数字：128K 上下文、890 字节/token → \(K\approx114\) MB；若互联带宽 \(W=200\) GB/s、\(\eta=0.2\)，则 \(R<40\) GB/s ÷ 114 MB ≈ 351 请求/秒。**超过这个请求率，PD 分离就会被传输拖垮，除非跨池互联带宽再上一个量级。** 这解释了为什么 PD 分离只在高速互联域内做，也解释了为什么"KV 压缩"（§2）与"PD 分离"是互补而非替代——压小 \(K\) 直接抬高可分离的请求率上限。

**练习 6（对应退出标准 6）**
DeepInfer 公开了内核与并行层，但明确不含 KV cache 管理、PD 分离编排、负载均衡、API 传输层。若你的团队要基于它搭一个生产服务，请列出还缺的四块、各自要解决的决策点，并指出其中哪一块最容易被低估。

**参考答案：**
① **KV cache 持久化与换入换出**：分层放哪里（HBM/主机内存/SSD）、换出策略（LRU/按会话优先级）、换入预取时机。
② **PD 分离执行编排**：prefill/decode 池比例怎么定、KV 传输走哪条通道、失败时如何回退到同机执行。
③ **副本负载均衡**：请求如何分发到 data-parallel 的 prefill/decode worker、如何感知各副本的 KV 命中率做亲和路由（把同源会话打到同一副本能提命中率）。
④ **API 与可观测**：HTTP、鉴权、配额、重试、限流、 admission control、指标采集。
**最容易被低估的是③**：负载均衡不只是"均匀分发"，还要做**前缀亲和路由**——把共享前缀的请求路由到已缓存该前缀的副本，命中率能差数十个百分点，直接影响 TTFT（见 §3）。第二容易低估的是①：换出策略做错会导致 SSD 带宽被打满，延迟比不做换出还差。
