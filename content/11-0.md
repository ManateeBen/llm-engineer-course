## why

前面 8 个阶段默认算力是 NVIDIA GPU。但在国内做 LLM 工程，你迟早要面对另一个现实：**卡可能是昇腾、寒武纪或海光，且这个比例还在上升**（公开市场报道显示国内 AI 加速卡份额已从 NVIDIA 近乎垄断转为昇腾占据半数左右的量级）。

而"换卡"这类任务最容易被低估。常见误解是"把 CUDA 换成 CANN、把 PyTorch 换成 torch_npu 就行"——实际上变的是四条线：**架构**（计算单元的组织方式）、**编程模型**（怎么写算子）、**数据格式**（低比特表示）、**互联**（多卡怎么连）。其中任何一条理解偏差，都会让你在项目后期付出数倍代价。

本单元给你一张"差异地图"，目标是让你在评估、选型、迁移时知道该问什么问题。11-2 再讲具体怎么迁。

## body

### 1 先看清单：国产算力有几条技术路线

国产 AI 加速卡不是一家，而是**三条截然不同的技术路线**：

| 路线 | 代表 | 架构取向 | 编程生态 | 迁移难度 |
|---|---|---|---|---|
| **NPU（专用架构）** | 华为昇腾 | 达芬奇架构：Cube（矩阵）+ Vector（向量）+ Scalar（标量）三条独立流水线 | CANN + Ascend C，PyTorch 经 torch_npu 适配 | 高：编程模型不同 |
| **MLU（专用架构）** | 寒武纪 | MLU Core，自研 ISA，片内存储层次自行设计 | Cambricon BANG C / NeuWare，PyTorch 适配层 | 高 |
| **GPGPU（兼容路线）** | 海光 DCU | 通用 GPU 架构，走 ROCm 生态 | 接近 CUDA/HIP 的编程体验 | 中：生态兼容度高 |
| 其他 | 昆仑芯、天数智芯、沐曦、摩尔线程等 | 各有取向（GPGPU 或 NPU） | 各自的运行时与适配层 | 视路线而定 |

**第一条要建立的判断**：迁移成本与"架构离 GPU 多远"成正比，不是与"品牌"成正比。走 GPGPU/ROCm 路线的卡，很多 CUDA 代码能近乎平移；走 NPU 路线的，算子要重写或换库。

### 2 昇腾的架构：三条流水线，不是一种 core

GPU 的计算单元是**统一的 SIMT**：大量同构核心，每个核心既能做标量也能做向量，矩阵运算靠 TensorCore 这类专用单元加速。

昇腾 AI Core 是**异构分治**：

\[
\text{AI Core} \;=\; \underbrace{\text{Cube}}_{\text{矩阵}} \;\oplus\; \underbrace{\text{Vector}}_{\text{向量}} \;\oplus\; \underbrace{\text{Scalar}}_{\text{标量/控制}}
\]

- **Cube**：专用矩阵乘单元。一次指令完成 \(16\times16\times16\) 级别的矩阵块乘加（具体规模随代际变化），是算力峰值的主要来源。**只有规整矩阵乘能吃满它**
- **Vector**：向量运算单元。激活函数、归一化、逐元素、归约都在这里。带宽敏感型算子的主战场
- **Scalar**：标量运算与流程控制，负责地址计算、循环与分支

存储是**显式分层的**：

\[
\text{寄存器} \;\subset\; \text{L0} \;\subset\; \text{L1 / UB（统一缓冲区）} \;\subset\; \text{L2} \;\subset\; \text{HBM}
\]

与 GPU 的关键差别：**数据在层间的搬运要显式管理**（GPU 的 cache 对程序员相对透明）。这带来两个后果：

1. **编程负担更重**：你要显式安排"什么时候把哪块数据搬到哪层"
2. **优化上限更高**：把搬运排好（流水编排）后，效率可以非常接近硬件极限——这正是 DeepGEMM-Ascend 能报到 99.8% 硬件极限的原因

> 比喻：GPU 像有个勤快服务员的自助餐厅，你伸手他就给你拿（cache 帮你兜底）；昇腾像后厨，你得自己写清楚"第 1 分钟从冷库搬到备菜台、第 2 分钟下锅"（显式流水）。麻烦，但排得好的话动线效率极高。

### 3 软件栈：CANN 对标 CUDA 的哪几层

把两条栈对齐着看，迁移时才知道自己在哪一层：

| 层次 | NVIDIA | 昇腾 |
|---|---|---|
| 驱动与运行时 | Driver / CUDA Runtime | Driver / **CANN Runtime**（ACL：Ascend Computing Library） |
| 算子编程语言 | CUDA C++ | **Ascend C**（兼容 C/C++，多层级 API）+ PyAsc/PyPTO（Python 前端） |
| 底层指令 | PTX / SASS | **PTO-ISA**（Tile 级虚拟指令集，8 大类 120+ 条虚拟指令） |
| 算子库 | cuBLAS / cuDNN | **CANN 算子库**（ops-nn、ops-transformer 等） |
| 图引擎 | TensorRT / CUDA Graph | **GE（Graph Engine）** + aclGraph |
| 通信库 | NCCL | **HCCL**（Huawei Collective Communication Library） |
| 训练框架 | PyTorch / Megatron | **MindSpore**；PyTorch 经 **torch_npu** 适配 |
| 工具 | Nsight / nvprof | **MindStudio** / Profiling 工具 |

**迁移时的第一个决策点**：你的代码落在哪一层？

- 只用 PyTorch 高层 API、不写自定义算子 → 通常 `import torch_npu` 级别的工作量
- 用了 CUDA 自定义算子 → 必须重写（11-2 讲方法）
- 依赖 NCCL 的特定通信模式 → 换成 HCCL，语义基本一致但性能特征可能不同

### 4 数据格式：低比特已经有了自己的标准之争

NVIDIA 生态的事实标准是 FP8（E4M3/E5M2，2022 年由 OCP 标准化）。昇腾推的是 **HiFloat8**：据华为公开信息，HiFloat8 已完成芯片→算子→训推框架→模型的全流程验证，**训推精度与 BF16 平均误差在 0.5% 以内、性能较 BF16 提升约 30%**；2026 年完成团体标准、8 月在 TC28 完成国标立项，并已申请 IEEE study group，社区已有百余家单位加入。更低比特还有 **HiFloat4**，用 E6M2 全局缩放因子 + 2 级局部微阶码，在 4 bit 范围内提高元素表达精度。

**为什么这件事对你的工程有实际影响**：

1. **格式不互通**：在一个平台上标定好的 FP8 量化参数，不能直接搬到 HiFloat8 上用，要重新校准
2. **误差特征不同**：8 位浮点的差异在尾数/指数分配，直接决定哪些层会先崩
3. **硬件加速路径不同**：用错格式的算子可能走不了专用单元，反而更慢

判据还是 8-8 §2 那两条：**看相对误差（能不能用）与省下的带宽（值不值得用）**，并且要问清是在什么粒度（逐张量/逐通道/逐块）上测的。

### 5 互联：超节点把"通信"变成一等公民

大模型训练与推理早就不受限于单卡，而受限于**卡间互联**。昇腾侧的互联是 HCCS（片间）与超节点级方案。2026 年的一个标志性事件：华为与 DeepSeek **联合优化基于昇腾 950 的 128 卡超节点**，把合作从"算子级"推进到"系统级"——对 MoE 这种通信密集型模型，互联效率与芯片算力同等重要。

互联能力怎么量化？看集合通信的时间模型。以最常用的 **Ring AllReduce** 为例，传输 \(D\) 字节、\(N\) 张卡、链路带宽 \(B\)：

\[
T_{\text{allreduce}} \;=\; \underbrace{\frac{2(N-1)}{N}\cdot\frac{D}{B}}_{\text{带宽项}} \;+\; \underbrace{2(N-1)\,\alpha}_{\text{延迟项}}
\]

其中 \(\alpha\) 是每跳启动延迟。两个可读出的结论：

- **带宽项几乎与 \(N\) 无关**（\(\tfrac{2(N-1)}{N}\to2\)），所以 AllReduce 的带宽成本不随卡数爆炸——这是 Ring 算法的价值。严格地看，系数 \(f(N)=\tfrac{2(N-1)}{N}\) 对 \(N\) 的导数是

  \[
  f'(N) \;=\; \frac{2}{N^2}\;\xrightarrow[N\to\infty]{}\;0
  \]

  **边际增益按 \(1/N^2\) 衰减**：\(N=8\) 时 \(f=1.75\)，\(N=128\) 时 \(f=1.984\)，之后再加卡几乎不再改变带宽成本
- **延迟项随 \(N\) 线性增长**，卡数非常多时（超节点百卡级）延迟项会成为瓶颈，需要层次化算法（节点内 / 节点间分层归约）

> 这也解释了为什么超节点要"联合优化"：单看芯片算力没意义，算力/带宽/延迟三项共同决定端到端。**评估一张卡时，峰值 TFLOPS 是最不重要的那一项。**

### 6 怎么评测一张国产卡：别只看峰值

采购或选型时最常见的错误是对着峰值 TFLOPS 排序。正确的评测口径至少四层：

**第一层：单算子效率（微基准）**
\[
\eta_{\text{op}} \;=\; \frac{\text{实测算子吞吐}}{\text{硬件理论峰值}}
\]
DeepGEMM-Ascend 报的 99.8%（BF16 稠密 GEMM）、FlashMLA 的 410 TFLOPS/95%（prefill）、360 TFLOPS/83%（decode）、DeepEP 的 90~95%（dispatch 带宽）都属于这一层。**它能说明"硬件能力有没有被榨出来"，不能说明端到端快不快。**

**第二层：模型级效率（MFU）**
\[
\mathrm{MFU} \;=\; \frac{\text{实际达成的 FLOPs/s}}{\text{硬件峰值 FLOPs/s}}
\;=\; \frac{(\text{每 token FLOPs})\times(\text{tokens/s})}{\text{Peak}}
\]
训练场景 MFU 40~50% 已经是好水平；低于 30% 通常意味着并行策略或算子有问题。这一层才反映真实工程水平。

**第三层：端到端服务指标**
承 8-7：TTFT、TPOT、tokens/s/卡、前缀命中率、p99/p50。**成本是按这一层算的。**

**第四层：生态与工程成本（最难量化，但经常决定成败）**
- 你的模型用到的算子有没有现成实现？缺几个？补一个要多久？
- 训练框架、推理引擎、量化工具链是否齐备？
- 出了问题，社区/厂商响应速度如何？
- 团队现有技能迁移成本多大？

一条实用的经验：**先拿你的真实模型跑一遍端到端，而不是跑微基准**。微基准只用于定位瓶颈（8-1 §6 的三条纪律在这里同样适用）。同时记住厂商自测数字要打折扣——条件（形状、并行规模、拓扑、数据类型、模型版本）差一点，结论就能反。

### 7 一条冷静的判断

国产算力在**规整算子（GEMM）上已经追平甚至贴近硬件极限**（99%+ 的实测说明优化空间所剩无几），真正的差距在：

1. **长尾算子覆盖**：不是"能不能写"，而是"有没有人已经写好"
2. **工具链成熟度**：编译器报错信息、profiling 可视化、调试体验
3. **社区与案例密度**：遇到问题时能不能搜到答案
4. **代际连续性**：新架构发布后，算子多久能跟上（PTO-ISA 的"Tile 级抽象、代际兼容"正是冲着这一点来的）

所以评价"国产卡能不能用"，准确的问题不是"它跑不跑得动模型"，而是**"我要为它额外付多少工程时间"**。这个答案取决于你的模型有多常规、你的团队有多少性能工程能力，而不是取决于卡本身。

## ex

**练习 1（对应退出标准 1）**
说出昇腾 AI Core 的三条流水线及其各自负责什么，并解释：为什么一个以逐元素运算为主的算子（如 LayerNorm）在昇腾上吃不到芯片的峰值算力？

**参考答案：**
Cube（矩阵）、Vector（向量）、Scalar（标量/控制）。LayerNorm 的运算是逐元素的归约与仿射变换，只能在 **Vector** 单元上执行，而芯片的峰值算力主要由 Cube 单元贡献——**LayerNorm 根本用不上 Cube**。它同时受限于 HBM 带宽（算术强度 \(O(1)\)，承 8-1 §1），所以既吃不到算力峰值、又卡在带宽上。**含义：这类算子的优化方向是融合与减少搬运（8-1 §4），而不是指望架构给你算力。**

**练习 2（对应退出标准 2）**
把下表填完：CUDA Runtime / CUDA C++ / PTX / cuBLAS / NCCL / TensorRT 在昇腾栈中的对应物分别是什么？并指出：若你的项目用了 CUDA C++ 自定义算子，迁移时落在哪一层、工作量取决于什么？

**参考答案：**
CANN Runtime（ACL）/ **Ascend C**（+PyAsc、PyPTO）/ **PTO-ISA** / CANN 算子库（ops-nn、ops-transformer）/ **HCCL** / **GE（Graph Engine）** + aclGraph。
自定义算子落在**算子编程语言层**，必须重写。工作量取决于：① 算子是否能用 CANN 现成库或高阶 API 拼出来（能拼就几乎零成本）；② 是否需要手写流水与 Tiling（需要则按人周计）；③ 是否有精度对齐与性能验收要求（验收越严越久）。11-2 会给完整的迁移流程。

**练习 3（对应退出标准 3）**
用 Ring AllReduce 公式 \(T=\frac{2(N-1)}{N}\frac{D}{B}+2(N-1)\alpha\) 计算并比较：\(D=1\) GB、\(B=200\) GB/s、\(\alpha=2\) μs 时，\(N=8\) 与 \(N=128\) 各自的总时间，以及两项的占比。这说明了什么工程含义？

**参考答案：**
\(N=8\)：带宽项 \(\frac{2\times7}{8}\times\frac{1}{200}=1.75\times0.005=8.75\) ms；延迟项 \(2\times7\times2\mu s=28\) μs。**带宽项占 99.7%**。
\(N=128\)：带宽项 \(\frac{2\times127}{128}\times0.005\approx9.92\) ms；延迟项 \(2\times127\times2=508\) μs ≈ 0.51 ms。**带宽项占 95%**。
**含义**：即便到 128 卡，Ring AllReduce 的延迟项仍不是主导——因为它是 \(O(N)\) 但系数极小（μs 级）。真正的隐患在别处：① 实际链路带宽 \(B\) 在跨节点时可能掉一个量级，那时带宽项才爆炸；② 该公式假设链路无争用，实际训练中通信与计算重叠、且与数据并行/张量并行/专家并行的通信模式叠加。**所以它给的是下界，实测更差时要查拓扑与重叠率。**

**练习 4（对应退出标准 4）**
某卡 BF16 峰值 800 TFLOPS。你的模型每 token 需要 \(2\times 7\times10^9=1.4\times10^{10}\) FLOPs（承 8-0 的 \(6N\) 估算：每 token 约 \(2N\) FLOPs 前向、训练约 \(6N\)），实测训练吞吐 12000 tokens/s。求 MFU，并判断这个数字意味着什么（提示：训练时每 token 是 \(6N\)）。

**参考答案：**
训练每 token FLOPs \(=6N=6\times7\times10^9=4.2\times10^{10}\)。达成的 FLOPs/s \(=4.2\times10^{10}\times12000=5.04\times10^{14}\) FLOP/s \(=504\) TFLOPS。
\(\mathrm{MFU}=504/800=63\%\)。
**判断**：63% 是**相当高**的水平（业界 40~50% 已属优秀）。遇到这种数字，第一反应应该是**核查**而非庆祝：① \(N\) 是否只算了主干参数（激活参数、embedding、MoE 总参数都要口径一致）；② 是否把重计算的额外前向算进去了；③ 峰值口径对不对（稠密 vs 稀疏、是否含 sparsity 加成）。**MFU 超过 60% 时，先怀疑自己的分子分母口径，再怀疑硬件。**

**练习 5（对应退出标准 5）**
采购评审会上，厂商 A 给出"GEMM 达硬件极限 99.8%"的微基准，厂商 B 给出"某 7B 模型训练 MFU 42%"。你会怎么比较这两份材料？请给出至少三条质疑点和一个统一的评测方案。

**参考答案：**
三条质疑：
① **层次不同，不可直接比**：A 是算子级（第一层），B 是模型级（第二层）。算子 99.8% 与模型 MFU 42% 完全可以同时成立——算子厂已经榨干，但模型里有大量非 GEMM 的时间（通信、非融合算子、调度空隙、重计算）。
② **A 的条件缺失**：矩阵形状是什么？只测了规整 GEMM 还是包括 MoE 的 grouped GEMM？数据类型？并行规模？**换个形状可能掉一半。**
③ **利益关系**：两个数字都是厂商自测，未经独立复现。
统一评测方案：**拿自己的真实模型跑端到端**。固定：模型、并行策略、batch/序列配置、数据类型、目标 SLO（训练看 tokens/s 与 MFU，推理看 TTFT/TPOT/tokens/s/卡，承 8-7）。跑通后用 profiling 定位瓶颈，再用微基准**解释**瓶颈（而不是用微基准**选**卡）。同时把"补齐缺失算子需要多少人周"写进评估表——这是最容易被漏掉的真实成本。

**练习 6（对应退出标准 6）**
有人说"昇腾上的 GEMM 都到 99.8% 硬件极限了，说明国产算力已经追平 NVIDIA"。请用本单元与 8-1 的框架评价这个说法，指出它对在哪里、错在哪里。

**参考答案：**
**对的地方**：规整算子的优化确实接近物理天花板——GEMM 这类算子的形态简单、访存规整，只要投入工程就能贴到极限。这个数字说明昇腾的**硬件能力可以被充分释放**，不存在"硬件设计缺陷导致跑不满"的问题。
**错的地方**（三条）：
① **以偏概全**：GEMM 只是模型时间的一部分。MoE 的 grouped GEMM、稀疏注意力索引、专家通信这些"不规则"部分才是 2026 年的主战场，它们的效率远低于 99%（FlashMLA decode 是 83%、DeepEP 是 90~95%，且都是厂商自测）。
② **层次混淆**：算子级 99.8% 不等于模型级 MFU 高，更不等于端到端服务成本低。
③ **忽略了非硬件成本**：生态覆盖、工具链、社区案例、代际维护（8-1 §7 讲过自研内核的长期维护成本，在国产平台上这个成本更高，因为可参考的实现更少）。
**准确的结论应该是**：国产算力在"能不能跑满硬件"上已经过关，差距在"有多少现成的东西可复用"与"端到端工程效率"上。
