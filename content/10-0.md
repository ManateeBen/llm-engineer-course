## why

LLM 的知识冻结在训练截止时刻，幻觉（6-x 讲过）在长尾事实上最严重。RAG 的解法是**把"记忆"外包给检索系统**：查询时先从知识库捞出相关文档，再把文档塞进上下文让模型基于证据回答。这是生产环境里最廉价、最可控的能力扩展——不用重训模型，换知识库即可。本单元讲完整管线：chunk 策略、embedding 双塔、向量库 ANN 检索、BM25+dense 混合、重排，以及 RAG 评测（忠实度/引用质量）。这是 Agent 阶段的地基，也是你 SRE 背景最容易迁移的技能（检索系统本质是分布式存储 + 索引工程）。

## body

### 1. 管线的五段解剖

```
文档 → chunk → embedding → 向量库索引
                              ↓
查询 → [查询理解] → 混合检索(top-k) → 重排(rerank) → 拼 prompt → LLM
```

**chunk 策略**是第一个隐藏陷阱：固定 512 token 切分会把一个完整论证切成两半，检索时两半都召回、两半都不完整。工程对策：

- **语义 chunk**：按标题/段落边界切（Markdown 结构天然边界）
- **重叠窗口**：相邻 chunk 重叠 10~20%，缓解边界切断
- **小块索引 + 大块生成**：索引按 256 token 存（检索精度高），命中后回溯扩展到父块 1024 token 喂 LLM——**small-to-big 是当前生产标配**

**embedding**：双塔编码器（查询塔 + 文档塔独立编码，点积算相似度）。训练信号与 CLIP 的 InfoNCE 同构（9-1）——hard negatives 的质量决定检索器上限（batch 内随机负样本太容易，要用 BM25 召回的非相关文档 + 同 batch 其他文档的正面样本做难负例）。

### 2. 混合检索：为什么 dense 赢不了 BM25

dense 检索（向量语义匹配）与 sparse 检索（BM25 词项匹配）的失效模式互补：

| | dense | BM25 |
|---|---|---|
| 强项 | 同义改写（"车厘子"≈"樱桃"） | 精确词项（错误码、型号、专名） |
| 弱项 | 数字/罕见词/OOV | 语义泛化 |
| 失效例 | "ERR_CONNECTION_REFUSED" 向量化后语义漂移 | "怎么修网络"匹配不到 "连接被拒绝" |

**混合公式**（RRF，倒数秩融合）：

\[
\text{score}(d) = \sum_{r\in\{\text{BM25},\text{dense}\}}\frac{1}{k + \text{rank}_r(d)}
\]

RRF 不需要分数归一化（两个检索器的分数尺度不可比）——只用排名。**这是工程上最鲁棒的融合方式**，加权融合需要调尺度、RRF 只需要调 \(k\)（典型 60）。

### 3. 重排：cross-encoder 的二次精排

第一级检索（双塔）是"查询和文档独立编码后点积"——快但粗（百万级文档毫秒级）。第二级 rerank 用 cross-encoder：**查询和文档拼接后一起过 BERT 类模型**，输出相关性分数——慢但准（每对一次前向）。

成本账：top-100 候选 × cross-encoder 前向（BASE 级 ~0.5 GFLOPs/pair）≈ 50 GFLOPs/查询 ⇒ GPU 上 50 ms 级；top-1000 则 500 ms——**重排深度是延迟与精度的直接交换**。典型配置：召回 1000 → BM25+dense RRF 融合取 100 → rerank 取 top-5~10 进 prompt。

### 4. RAG 的评测：三元组指标

RAG 不是"检索准就行"，是端到端系统。三元组评测：

1. **检索侧**：Recall@k（相关文档进 top-k 的比例）、MRR（第一个相关的排名倒数）
2. **生成侧-忠实度**：答案的每个声明能否被检索文档支持（用 NLI 模型或 judge 逐句核对）——**这是幻觉的 RAG 版度量**，没有检索支持却言之确凿 = 编造
3. **生成侧-有用性**：答案是否正确且完整（人工或 judge）

**典型失败模式**：检索 Recall@10 = 95%（检索没问题）但忠实度只有 70%（模型没用检索内容，在用自己的参数化知识回答）——**诊断出"模型忽略上下文"比"检索差"常见得多**。对策：prompt 里显式要求引用（"每个声明后附 [doc_id]"），引用率本身是忠实度的代理指标。

### 5. worked example：技术文档 RAG 的延迟-精度账

**场景**：内部运维知识库（10 万文档，SRE runbook 风格），查询"K8s pod CrashLoopBackOff 怎么排查"。

**配置**：BGE-M3 embedding（1024 维）、Milvus 向量库（HNSW 索引）、BM25（Elasticsearch）、bge-reranker-v2 重排。

**教学延迟预算**（各段假定耗时；真实端到端p50不能由分段p50直接相加）：

| 段 | 耗时 | 说明 |
|---|---|---|
| 查询编码 | 8 ms | GPU 推理一次 |
| 向量 ANN（10 万） | 12 ms | HNSW，ef=64 |
| BM25（10 万） | 15 ms | ES 标准 |
| RRF 融合 | 1 ms | 内存排序 |
| rerank top-100 | 180 ms | GPU batch 推理 |
| prompt 拼装 | 2 ms | 模板 |
| LLM 生成（top-5 上下文） | 800 ms | 7B，首 token 400 ms |

**按串行预算相加为1018 ms，约1.02 s**，瓶颈在 rerank（18%）与 LLM（78%）。

**优化路径**：① rerank 深度 100→50（180→90 ms，Recall@5 从 0.82 掉到 0.79——换 90 ms 买 3 点，值）；② LLM 用投机解码（8-8）降 40%；③ 缓存高频查询的检索结果（运维查询高度重复，命中率 30%+ 时检索段耗时直接归零）——**查询缓存是 RAG 系统 ROI 最高的优化，因为知识库查询分布长尾且重复**。
