## why

8-1 教你手写内核：roofline 定位、瓦片用 AM-GM 算。但模型有几百个算子，手写是不可能的——于是答案交给编译器：torch.compile 一行命令提 MFU 数个点，Triton 让你用 Python 写出接近 CUDA 的内核，MLIR 在国产芯片上把同一份模型降级到完全不同的指令集（11-2 的核心依赖）。

"编译器"听起来吓人，骨架其实只有三件事：**把程序表示成图 → 在图上做等价变换（融合/布局/调度）→ 把每个节点降到 tile 与指令**。本单元把骨架讲清，让你能读懂 `torch.compile` 的日志、判断什么情况下编译白做、以及为什么 Triton 的"块级"抽象是过去十年算子生产力的最大升级。

## body

### 1 三层 IR：编译器的主干管线

主流 AI 编译器共享同一分层（张量级别 → 块级别 → 指令级别）：

\[
\underbrace{\text{计算图}}_{\text{算子级}}\;\longrightarrow\;\underbrace{\text{tile 级程序}}_{\text{Triton / TileLang}}\;\longrightarrow\;\underbrace{\text{指令级}}_{\text{PTX / Ascend PTO-ISA}}
\]

- **图捕获**：把 eager 执行记录成静态图（TorchDynamo 的 bytecode 拦截 / FX trace）。难点是**动态性**：Python 控制流、动态形状。编译器用 **guard**（守卫条件）处理：每个编译产物附带"形状在此范围、分支走此路"的守卫，运行时守卫不过就回退或重编译。
- **图改写（pass）**：算子融合、常量折叠、布局变换（NCHW/NHWC）、死代码消除。**最值钱的 pass 是竖直融合**（§2）。
- **内核生成**：每个融合后的节点交给块级 DSL（Triton/TileLang）或模板库（cuBLAS/DeepGEMM），tile 级程序再由后端（LLVM/PTX、CANN）降到指令。

### 2 竖直融合：一个一阶模型算清收益

融合的数学收益可以直接用 8-1 的框架算。三个逐元素算子 \(f_1,f_2,f_3\) 依次作用，各算子算术强度 \(O(1)\)（读 \(n\) 字节、写 \(n\) 字节、算 \(O(n)\)）。不融合：HBM 流量 \(3\times\)（读）\(+\;3\times\)（写）\(=6n\)。融合成一次遍历：读 \(x\) 一次 + 写 \(y\) 一次 \(=2n\)：

\[
\text{流量比} \;=\; \frac{2n}{6n} \;=\; \frac{1}{3},\qquad
\text{融合后算术强度} \;=\; \frac{3\times O(n)\ \text{FLOPs}}{2n\ \text{Bytes}}\;=\;1.5\ \text{FLOPs/Byte}\times\text{每算子常数}
\]

融合**不改变总 FLOPs，只改变流量**——把 \(k\) 个带宽受限算子的流量从 \(2kn\) 压到 \(2n\)，耗时近似除以 \(k\)。这就是 8-1 §4"融合是唯一方向"的定量版本。**融合的约束**：中间结果必须放得下片上（tile 级 SRAM），所以融合窗口受 SRAM 容量约束——这正是 Triton 把"tile 大小"交给你的原因。

### 3 Triton：块级编程模型为什么是革命

CUDA 的心智模型是**线程**：你写"我是第几个线程、我处理哪个元素"，把 65536 个线程的组织、共享内存的搬运、bank conflict 全背在身上。Triton 把抽象抬到**块**：

```python
@triton.jit
def add_kernel(x_ptr, y_ptr, o_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask)
    y = tl.load(y_ptr + offs, mask=mask)
    tl.store(o_ptr + offs, x + y, mask=mask)
```

你只声明"一个 program 处理 BLOCK 个元素"，**向量化、共享内存、线程映射全部由编译器推导**。代价：细粒度控制（warp 特化、异步拷贝流水）受限；收益：FlashAttention 类内核从数千行 CUDA 缩到两百行，且**可移植**——Triton 有 NVIDIA 与多家国产芯片后端（这是 11-2 迁移讨论里 FlagGems 路线的基石）。

**自动调优**：BLOCK、num_warps、num_stages 构成离散搜索空间，编译器对每个形状枚举/启发式选优（autotune）。**这意味着同一个算子在 A 卡与 B 卡上的最优配置不同**——可移植的是代码，不是配置。

### 4 图优化在推理侧：图与启动开销

推理引擎（8-7）对编译器的需求与训练不同，大头是**启动开销与内存规划**：

- **CUDA Graph / 静态图执行**：decode 每步跑几百个 kernel，每个启动 ~5 µs，纯启动就吃掉毫秒级预算的一部分；CUDA Graph 把整步录制成一次回放，启动开销从 \(O(\#\text{kernel})\) 降到 \(O(1)\)。**约束**：形状必须静态——KV cache 按块预分配（PagedAttention）正是为了配静态图。
- **连续批处理与图冲突**：batch 组成每步都变，与静态图冲突——工程解是"桶形"（bucketing）分档复用几个图，或像 8-7 的 DeepInfer 栈做全链路动态图优化。
- **量化图改写**：把 FP16 GEMM 改写为 FP8/INT8 + 量化/反量化节点（8-8），插入位置与数值误差传播在图层面统一规划，而不是逐算子手工改。

### 5 编译器的失效模式（什么时候白做）

1. **动态形状频繁重编译**：形状组合爆炸，guard 大量 miss，编译时间吃掉运行收益——判定指标：**编译产物命中率**。日志里 recompile 次数高就是红灯。
2. **内存受限的融合回退**：tile 放不下，编译器静默回退成未融合——要读生成的 kernel 数（融合前 N 个算子、融合后 M 个节点，M 应显著小于 N）。
3. **图断点（graph break）**：Python 侧的 print、数据依赖控制流把图切碎，碎图之间回退 eager——`torch.compile` 日志里的 graph break 列表要先清零再谈收益。
4. **算子已有手工极限内核**：GEMM 已是 DeepGEMM 级别（8-1），编译器生成的很难超越——**编译器的主战场是"胶水算子"与融合，不是大 GEMM**。

## ex

**练习 1（对应退出标准 1）**
画出 AI 编译器三层 IR 管线，标注每层的输入/输出表示，并说明 Triton 程序属于哪一层、CUDA 属于哪一层。

**参考答案：**
计算图（算子级：节点=matmul/softmax/…，边=张量）→ tile 级（节点=块程序：BLOCK 尺寸的循环嵌套，带调度注解）→ 指令级（PTX/PTO-ISA 等 ISA 指令流）。Triton 是 tile 级；CUDA 是指令级之上的线程级（介于两者之间：显式管理线程与共享内存，仍需 nvcc 降到 PTX）。**判读意义：抽象层级越高，移植性越好、可达峰值越低；TileLang/MLIR 的价值在于允许同一源码分层下沉。**

**练习 2（对应退出标准 2）**
用 8-1 的算术强度模型证明：\(k\) 个算术强度 \(O(1)\) 的逐元素算子融合后，HBM 流量从 \(2kn\) 降到 \(2n\)；再计算 \(k=5\)、每算子 0.5 FLOPs/Byte、卡带宽 8 TB/s 时融合前后的耗时比。

**参考答案：**
不融合：每个算子独立读写 ⇒ 流量 \(k\times(n_{\text{读}}+n_{\text{写}})=2kn\)；融合：一次遍历读 \(x\) 写 \(y\) ⇒ \(2n\)。\(k=5\)：流量比 1/5。耗时 = 流量/带宽：融合前 \(10n/8\times10^{12}\)，融合后 \(2n/8\times10^{12}\)，**耗时比 5:1**。注意中间态：若编译器只融合了其中 3 个（SRAM 限制），耗时比 = 5/3 ≈ 1.67——**收益随融合窗口缩小线性退化**，所以要看实际融合结果而不是"开了 compile"。

**练习 3（对应退出标准 3）**
解释 Triton 的 `mask=offs<n` 解决什么问题，以及为什么 CUDA C 里这个问题由"网格尺寸凑整 + 越界判断"由程序员自己管。

**参考答案：**
真实张量长度 \(n\) 常不是 BLOCK 的倍数，最后一个 program 会算出越界偏移；Triton 用 mask 让越界 lane 的 load/store 变成 no-op（load 返回 0 或指定 other），**边界处理进入块抽象**。CUDA 里网格尺寸是程序员算的（\(\lceil n/\text{BLOCK}\rceil\)），越界判断是 `if (idx < n)` 手写——错一个就是越界写。**抽象红利的具体体现：同一类正确性 bug 在块级模型里被系统性消除。**

**练习 4（对应退出标准 4）**
decode 服务每步 400 个 kernel、启动各 5 µs。算 CUDA Graph 前后的启动开销；若单步计算 3 ms，开销占比从多少降到多少？并说明 PagedAttention 与 CUDA Graph 的配套关系。

**参考答案：**
前：\(400\times5\,\mu\text{s}=2\,\text{ms}\)，占比 \(2/5=40\%\)（单步总 3+2=5 ms）；后：1 次回放 ~10 µs，占比 \(10/3010\approx0.3\%\)。配套关系：CUDA Graph 要求每步 kernel 序列与张量地址固定 ⇒ KV cache 必须预先按固定块布局（PagedAttention 的块表），动态 batch 则用桶分档（几个固定 batch 尺寸各录一张图）。**没有静态化的内存，就没有静态化的图。**

**练习 5（对应退出标准 5）**
某团队对 decode 服务开 torch.compile 后吞吐反降。日志显示：recompile 247 次、graph break 13 处、融合节点数 89/412。诊断三个问题并给出对应修法。

**参考答案：**
① recompile 247 次 = 动态形状爆炸，编译时间占运行时间 ⇒ 开 dynamic=True 或形状桶化，让守卫命中；② graph break 13 处把图切碎、碎段回退 eager ⇒ 清日志里的 break 源（print/数据依赖分支/第三方 op），包不住的部分手动隔离；③ 融合 89/412 说明大量算子没融上（内存回退或模式不识别）⇒ 检查 SRAM 限制与布局，必要时手动标记融合边界。**方法论：编译优化必须看产物（融合率、命中率、break 数），不能只看开关。**

**练习 6（对应退出标准 6）**
判断下列优化该交给编译器还是手写内核：(a) RMSNorm+残差加+量化；(b) 4096×4096×4096 的 BF16 GEMM；(c) 新的稀疏注意力模式（原型阶段）；(d) 已稳定的 TopK 热路径（占比 18%）。逐项给理由。

**参考答案：**
(a) **编译器/模板融合**：典型竖直融合场景，模式标准，收益大风险小。(b) **手写/厂商库**：大 GEMM 是 compute-bound，拼指令级极限（张量核调度、双缓冲），编译器很难超过 DeepGEMM/cuBLAS。(c) **Triton 快速原型**：模式新、正确性优先，块级 DSL 的生产力优势最大；稳定后再决定是否下沉。(d) **手写**：占比高（18%）+ 模式稳定 + 收益确定，投资回报最高。**判据三要素：算子占比 × 距 roofline 的差距 × 模式稳定度。**
