## why

11-0~11-2 讲的是"国产硬件与框架怎么适配别人定义的模型"；本单元反过来：**国产模型自己定义的东西**。这不是锦上添花的生态介绍——DeepSeek-V3 的 MLA（KV cache 压缩一个量级）、MTP（推理加速的原生支持）、FP8 混合精度训练，直接改写 8-6 的显存账、8-7 的 KV 账本、8-1 的算子形态。做国产部署的人不懂这些架构选择，等于拿着 2023 年的账本算 2026 年的部署。本单元按"架构创新 → 训练方法 → 部署决策"的顺序过一遍主要玩家。

### 1 生态版图：开源策略比模型本身更重要

| 系列 | 代表 | 开源程度 | 对部署者的含义 |
|---|---|---|---|
| **DeepSeek** | V3（671B MoE）/ R1 推理 | 权重 MIT + 完整技术报告 | 私有部署的首选 MoE；架构创新最多 |
| **Qwen（通义）** | Qwen2.5/3（0.5B~235B，dense+MoE）+ VL 系列 | Apache 2.0 全尺寸 | 全尺寸覆盖，vLLM/SGLang 一等公民，**默认起点** |
| **GLM（智谱）** | GLM-4/4.5 系列 | 部分权重开放 | ChatGLM 传统优势在中文；API 生态（MaaS）强 |
| **Kimi（月之暗面）** | K2（1T MoE，32B active） | 权重开放 | MuonClip 优化器实践；agentic 能力导向 |
| 其他 | Hunyuan（混元）、Yi、Baichuan、MiniMax | 各异 | 垂直场景/中文能力各有侧重 |

**判断一家模型值不值得私有部署，看三件事**：① 权重与 license（能否商用、有无地域限制）；② 架构是否在主流推理引擎支持矩阵里（vllm-ascend/SGLang 的适配进度——11-4 的两条路线在此落地）；③ 技术报告的诚实度（训练细节、失败模式敢不敢写——R1 报告连"语言混杂"的失败都写了，这种报告参考价值最高）。

### 2 DeepSeek-V3：三个改变账本的架构创新

**MLA（Multi-head Latent Attention，3-3 的承接）**。标准 GQA 把 KV 头数从 32 压到 4~8；MLA 走得更远——把 KV 投影到一个**低秩潜向量**（512 维 latent + 64 维 RoPE 分量，共 576 维/层），推理时只缓存这个联合压缩表示。按 V3 配置（\(L=61\) 层）算 KV 账本：

\[
\text{KV/token}_{\text{MHA}(128\text{头})}=2\times61\times128\times128\times2\,\text{B}\approx4.0\ \text{MB}
\]

\[
\text{KV/token}_{\text{MLA}}=61\times576\times2\,\text{B}\approx70\ \text{KB}
\qquad\Rightarrow\qquad \text{压缩} \approx 57\times
\]

注意两个诚实口径：① 对比基线若是 8 组 GQA（125 KB/token），压缩只有约 1.8×——**MLA 的"大数字"是相对全 MHA 的**；② MLA 的真正收益在**质量不降前提下的长上下文容量**：解码时用吸收矩阵（absorb）把投影并进 Q/K 计算，等效"每头独立 KV 但只存一份 latent"——同显存下能开的并发/上下文是数量级差异（8-7 的容量上限直接由它决定），这是 V3 采用它的原因。

**DeepSeekMoE**：细粒度专家（每 token 激活 8~16 个细专家）+ **共享专家**（始终激活，承载通用知识）+ 无辅助损失的负载均衡（用 bias 项动态调节，替代 aux-loss 对模型质量的干扰）。对并行的含义：EP 通信更重（8-4/8-5 的 all-to-all 是 MoE 的主要税），DeepEP 就是为它写的。

**MTP（Multi-Token Prediction）**：训练时每步预测多个后续 token。两个收益：① 训练信号密度高（等价数据增强）；② **推理时可作投机解码的草稿模型**——MTP 模块原生就是 draft head，8-8 的投机解码不用外挂小模型。部署时 EAGLE/MTP 式投机加速的接受率比通用草稿模型高一个档。

**FP8 混合精度训练**：细粒度 per-block scaling 的 FP8 GEMM（DeepGEMM，8-1 §6 的实测 99.8% 硬件极限）+ FP8 累进方案——这是 8-0 的算力账在国产/出口卡上"省着算"的标杆：V3 用 FP8 训练把单卡 MFU 推到 40%+ 档，等于**同样的卡多训一倍 token**。

### 3 DeepSeek-R1：GRPO 的完整工业报告

6-2 讲的方法论，R1 给的是完整配方细节：纯 RL（无 SFT 冷启动）的 R1-Zero 涌现反思、正式版四阶段管线（冷启动 → 推理 RL → 拒绝采样 SFT → 全场景 RL）、以及**蒸馏矩阵**（R1 生成的数据蒸馏 Qwen/Llama 小模型，32B 蒸馏版数学超过 o1-mini）。对 infra 的含义：R1 类模型的训练 = 大规模 GRPO rollout 集群（6-6 的速率失配、沙箱评测），推理侧 = 长思考的 KV 压力测试（MLA 的收益在这里兑现）。

### 4 Qwen：全尺寸 + 生态位

Qwen 的打法不是单点架构创新，是**全尺寸 × 全模态 × 宽松 license**：0.5B 到 235B 每档都有 dense，外加 A3B 类 MoE（激活参数小、总参数大——部署时按激活算力付钱）；Qwen-VL 系列是 9-2 的多模态底座；Apache 2.0 允许商用与二次开发。对私有部署者：**没有明确偏好时选 Qwen dense 中档**（7B/14B/32B）——生态适配最全、行为最可预期；要省算力上 MoE 档（A3B/A22B 类：总参数 100B+ 但每 token 只激活 3B，显存按总参数、算力按激活参数——**显存与算力解耦**，这正是 8-2 的 EP 切分的用武之地）。

### 5 GLM 与 Kimi：两条差异化路线

- **GLM（智谱）**：ChatGLM-6B 起的开源传统，GLM-4/4.5 走"通用能力 + 工具调用 + MaaS 服务"；架构上 GLM 系列的 pre-norm 与位置编码方案有自身演进（2D RoPE 的早期实践在 3-1 的语境里）。开源策略：部分权重 + API 优先，适合"用 API 验证、按需私有化"的路径。
- **Kimi K2（月之暗面）**：1T 总参/32B 激活的 MoE，**MuonClip 优化器**（Muon 的谱归一化 + QK-clip 抑制 attention logit 爆炸——这是 5-2"训练不稳定"的一个具体解法案例）；agentic 数据导向（工具调用轨迹大规模训练，10-1 的语境）。K2 的开源把"万亿 MoE 可训练"变成了公开事实。

### 6 部署决策：Worked example（V3 的账）

DeepSeek-V3 私有部署的最低配置核算（承 8-6 的静态显存口径）：

| 项 | 数值（BF16 推理口径） |
|---|---|
| 权重 671B×2B | 1342 GB（FP8 权重 671 GB） |
| KV/token（MLA） | ≈70 KB（\(L=61\)，576 维/层，BF16） |
| 单请求 32K 上下文 | ≈2.3 GB |
| 8×80 GB = 640 GB | FP8 权重 671 GB **装不下** ⇒ 至少 16 卡（1280 GB）或 EP 切分 |
| 16 卡部署 | 权重占 52%，余 609 GB KV 预算 ≈ 870 万 token ≈ **260 条 32K 并发** |

对比同档 dense（假设 300B dense，权重 600 GB BF16，KV 按 MHA 8 头 ≈ 125 KB/token）：**KV 预算只差 2~8 倍于 V3，且 dense 每 token 算力全量激活**——V3 的 37B 激活意味着 decode 的权重搬运每 token 只搬激活部分（MoE 的稀疏红利，8-2 §EP）。**结论：国产 MoE 旗舰的部署经济性 = FP8 权重 × MLA KV × 稀疏激活三者相乘**，任何一项用不上（引擎不支持 MLA、卡不支持 FP8），部署成本数量级上升——这是 11-2"迁移五步法"要逐个验证的东西。

## ex

**练习 1（对应退出标准 1）**
从 KV 账本解释 MLA 对推理部署的三大影响，并指出引擎侧必须支持什么才能兑现。

**参考答案：**
影响：① 长上下文容量：KV/token 从 MHA 的 4 MB 降到 MLA 的 ~70 KB（约 57×；相对 8 组 GQA 约 1.8×），32K 上下文的单请求 KV 从 131 GB 降到 2.3 GB——8-7 的并发上限直接翻数量级；② decode 带宽：KV 读写是 decode 的第二大搬运项（权重之后），KV 压缩 ≈ 带宽再省一份；③ 显存静态压力：激活显存 34sbhL 里的 KV 项缩小，重计算压力下降。引擎侧必须支持：MLA 的投影/吸收矩阵实现（Q 侧吸收 vs K/V 侧吸收两种形态）、paged KV 对压缩格式的分页管理（8-7 的 PagedAttention 要适配非连续 latent 格式）、投机解码的 MTP head 接入（8-8）。**任一项缺失，MLA 就是"权重里存着但用不上"的死重量——这正是 11-4 强调"移植先验证形态兼容"的原因。**

**练习 2（对应退出标准 2）**
Qwen A3B（总参 100B、激活 3B）与同系列 7B dense 的部署账对比：显存、decode 算力、EP 需求。

**参考答案：**
显存（BF16）：A3B 总参 100B ⇒ 200 GB（或 FP8 100 GB）；7B dense ⇒ 14 GB。decode 算力：A3B 每 token 只激活 3B ⇒ 前向 FLOPs \(2\times3\times10^9\)（与 7B dense 的 \(1.4\times10^{10}\) 同量级——**激活算力才是 decode 搬运/计算的主项**）。EP 需求：A3B 总参大，单卡放不下 ⇒ 必须 EP 切分（专家分布到多卡）+ all-to-all 通信（8-4/8-5）；7B dense 单卡可装。**结论：A3B 用"显存×2 卡以上 + 通信税"换"更好的质量/激活比"；7B dense 是"单卡简单部署"——选型按显存预算与通信条件，不按总参数字。**

**练习 3（对应退出标准 3）**
FP8 训练把 V3 的单卡 MFU 推到 40%+ 档。用 8-0 的 MFU 三因子框架解释 FP8 贡献了哪一项，并指出它不贡献的两项。

**参考答案：**
三因子 = kernel 效率 × 非矩阵算子稀释 × 并行税。FP8 贡献第一项：DeepGEMM 的 FP8 kernel 达到硬件极限 99.8%（8-1 §6）——矩阵乘这个最大耗时项效率拉满。不贡献：① 非矩阵稀释——softmax/LayerNorm/激活的耗时不变（甚至 FP8 下格式转换节点变多，略微恶化）；② 并行税——通信量与并行策略不变（TP/PP/EP 的 all-reduce/bubble 照付）。**推论：FP8 训练的 MFU 收益有上限（第一项的理论上限 ~100%→40% 档），再往上必须啃第二、三项——这也是 8-2~8-5 在 FP8 时代仍然成立的原因。**

**练习 4（对应退出标准 4）**
MTP 在推理时如何加速？给出接受率与吞吐的关系式，并指出 MTP 相对"外挂小模型做投机解码"的优势。

**参考答案：**
MTP 模块每步预测后续 \(k\) 个 token 的分布，作为草稿；目标模型一次验证 \(k\) 个（单次前向，成本 ≈ 1 次 decode + 验证开销），按 8-8 的接受率机制：每步期望产出 \(1+(k-1)\alpha\) token（\(\alpha\) 为平均接受长度）。吞吐 ≈ \((1+(k-1)\alpha)/t_{\text{step}}\)。MTP 的优势：① 草稿头与主模型**共享训练**（MTP 是训练目标的一部分，不是外挂）——分布对齐好，\(\alpha\) 通常高于"任意小模型草稿"；② 无额外显存（草稿模型通常 \(\frac{1}{10}\Psi\)，MTP head 只有几个 MB~百 MB 级）；③ 推理引擎只需接入现成 head。**代价：MTP 头是为"接下来几个 token"训练的，与主模型的残差分布有偏，长草稿的尾部接受率衰减——k 取 2~4 最优。**

**练习 5（对应退出标准 5）**
给三个场景选国产模型：① 单卡 4090（24 GB）客服知识库问答；② 16 卡 A800 集群高并发数学推理 API；③ 边缘盒子（无独显）意图分类。说明选型与部署形态。

**参考答案：**
① 单卡 24 GB：Qwen dense 小档（7B BF16 14 GB 权重 + KV 预算 ~10 GB，可行）——生态最全、单卡装得下；或 Qwen2.5-3B/7B-Instruct 直接 vLLM 起。② 16 卡高并发数学推理：DeepSeek-R1 蒸馏版（32B，推理强）或 Qwen MoE 档；16×80 GB 装得下 FP8 权重，MLA/EP 兑现 KV 压缩 + 稀疏激活——**前提是引擎对 MLA/MTP 的支持已验证**（11-2 五步法先跑形态验证）。③ 边缘：Qwen0.5B/1.5B 或 GLM 小档 INT4 量化（11-5 的端侧账：权重 ~0.5 GB、带宽下界 <10 ms/token）——dense 小模型 + llama.cpp/onnxruntime（11-5 §3）。**共同原则：先算账（8-0/8-6/11-5 的账本）再选型，不按跑分榜单选。**

**练习 6（对应退出标准 6）**
某团队要把 DeepSeek-V3 私有化，ICT 只说"支持大模型部署"。列出部署前必须验证的五个技术项（按 11-2 的方法论），各给一个具体验证方法。

**参考答案：**
① 权重加载与分片（671B FP8 分片到 16 卡的切分格式与引擎读取）——用引擎官方 checkpoint 转换脚本 + 单节点 smoke test；② MLA 算子支持（吸收矩阵两种形态、FP8 KV cache）——跑 8-1 的算子 micro-bench（MLA decode kernel 的实测 tokens/s vs 理论下界）；③ MoE all-to-all 通信（EP 下的 DeepEP/HCCL 拓扑探测）——nccl-tests/DeepEP 官方测试脚本在不同 EP 分组下的带宽；④ FP8 推理精度（FP8 权重 + FP8 KV 的端到端输出质量 vs BF16 参考）——11-2 五步法的精度对齐（同 prompt 比对中间激活）；⑤ 投机解码 MTP 接入（引擎是否支持、接受率实测）——8-8 的口径跑接受率-吞吐曲线。**五项全过再谈 SLA；任何一项"理论支持"都要落到实测数字——ICT 的"支持大模型"不等于"支持这个架构的模型"。**
